# Codex Agent Identity MVP 技术选型

## 目标

为当前 `文件优先单进程` 的 Codex `agent_identity` MVP，以及后续项目迭代，选择一条连续、低迁移成本、适合 MCP 演化的技术路线。

## 当前约束

- 当前仓库仍处于研究和文档阶段
- MVP 要优先保证链路跑通和可验证
- MVP 采用 `文件优先单进程`
- 后续希望能自然演化到 Codex / Claude 可接入的服务形态
- 当前不追求高性能和复杂分布式能力

## 候选路线

### 方案 A：TypeScript + Node.js

适合点：

- 文件优先 CLI 原型实现自然
- JSON、Schema、文件 I/O、目录管理都很顺手
- 后续接 MCP 服务可以沿同一代码基继续演化
- 与 Codex / MCP 生态贴合度高
- CLI、stdio、Streamable HTTP 都有成熟路径

风险：

- 需要尽早控制工程复杂度，避免前端式依赖膨胀

### 方案 B：Python

适合点：

- 原型速度快
- 数据处理和实验性逻辑表达灵活
- 写验证脚本方便

风险：

- 若后续很快进入 MCP 服务化，版本演化与依赖管理成本更高
- 当前项目重点不是研究脚本，而是可持续演化的运行骨架

### 方案 C：Go

适合点：

- 后期服务稳定性强
- 单二进制部署简单

风险：

- 对当前“极简原型 + 快速迭代验证”阶段收益不足
- 开发摩擦高于 TypeScript

## 结论

推荐主栈：

- `TypeScript + Node.js`

推荐理由：

- 最适合当前 `文件优先单进程` MVP
- 最容易在不换栈的前提下演化为 MCP 服务
- 最符合 Codex 环境的工具链与后续接入方向

## 推荐技术组合

### 核心运行时

- 运行时：`Node.js`
- 语言：`TypeScript`
- 包管理：`pnpm`
- 本地开发运行：`tsx`

### 数据与校验

- schema 校验：`zod`
- 文件格式：`JSON`
- 持久化：本地文件目录

### 测试

- 测试框架：`vitest`
- 验证方式：
  - CLI 黑盒测试
  - 文件产物校验
  - fixture 驱动目录验证

## 为什么第一版不用 Markdown 或 Obsidian 作为主运行格式

- MVP 当前重点是运行链路，而不是知识沉淀体验
- JSON 更适合强结构、最小校验和 CLI 处理
- Obsidian / Markdown 更适合作为后续长期知识层，而不是运行时主存储

## 为什么第一版不用数据库

- 数据库会过早把焦点拉到存储设计
- 当前最重要的是把身份加载、短期写入、长期落点、回读验证先串起来
- 文件优先更容易观察目录边界和失败路径

## 演化路线建议

### 阶段 1：MVP

- `TypeScript + Node.js`
- 单进程 CLI
- 文件优先
- 短期记忆与长期记忆分目录部署

### 阶段 2：服务化入口

- 在同一代码基上增加 MCP server 入口
- CLI 与 MCP 共享同一套核心逻辑

### 阶段 3：局部增强

- 为短期记忆引入轻量索引或 SQLite
- 长期知识层继续保持文件优先

## 当前建议冻结项

这轮技术选型建议先冻结以下内容：

- 主语言：`TypeScript`
- 运行时：`Node.js`
- 包管理：`pnpm`
- 本地运行：`tsx`
- schema 校验：`zod`
- 测试：`vitest`
- 文件格式：`JSON`

## 暂不冻结项

- 是否第一版就引入 MCP SDK
- 是否在 MVP 后立即引入 SQLite
- 最终部署方式是纯本地 CLI、stdio MCP，还是 HTTP MCP
